# 先说结果

## 基本模板提示词

```prompt
... 描述你要找什么文献 ...

使用英文进行搜索，你拿到搜索结果的JSON对象后，确认source字段是期刊出版商，且url字段包含该出版商的域名，仅保留符合要求的结果，舍弃不符要求或信息不全难以判断的结果
过滤后的结果按以下格式汇总，{key}由JSON对象中的对应字段内容填入，并逐字检查避免填错，尤其是{url}：
# {title}
- 来源: {source}
- 主要内容: {snippet}
- 网站链接: {url}
```

> [!note] 这个提示词效果非常好，虽然偶尔有填错的网站链接，但标题一定能搜到。

# 背景知识

## 为什么 LLM 会编文献

这叫 **AI 幻觉**（Hallucination）。*大语言模型*（Large Language Models，LLM）本质是**文字接龙模型**，输入输出都是文字，下一个字是**概率驱动**的。这是使用 LLM 输出可靠信息的一大阻碍。

## 一个文字模型是如何联网搜索的

所谓的联网搜索（或其他功能）都是**开发商写好的程序（函数接口）**，供 LLM 调用。LLM 输入输出都是文本，这意味着函数的**参数（输入）** 和**返回值（输出）** 也都是**文本**。

## 提高可靠性的最强原则

> [!note] LLM 具有不确定性，但函数逻辑是绝对固定的，因此参数和返回值的格式也是高度固定的。

只要知道具体的格式，就能在文献检索时带来极大的确定性。

**怎么知道格式？直接问它：**

```prompt
你在进行联网搜索时，向搜索服务商发起的请求是什么格式的，返回给你的搜索结果是什么格式的？
```

# 实践

## 搜索结果的 JSON 格式

以 *Gemini 3* 为例，它从 Google 拿到的搜索结果是这样的 JSON 对象：

```json
{
    "results": [
        {
            "title":"标题",
            "source":"来源/网站名",
            "snippet":"网页摘要",
            "url":"网页链接",
            ... 其他字段
        },
        ... 其他结果
    ]
}
```

> [!note] 这个 JSON 对象是**函数返回**的结果格式，内容**高度可靠**，因为它直接来自 Google 搜索服务。

我们实际只需要 LLM 帮忙**筛选和整理**，但它无时无刻都想去创作（因为给 AI 引入随机性的目的类似于蒙特卡洛模拟：没有能力直接给出最优解，又没有时间穷举所有解，就用随机采样覆盖解空间）。

## 针对性指令

既然知道 `title`、`source`、`snippet`、`url` 这些字段，就可以对 LLM 下更具针对性的指令：

```prompt
... 确认source字段是期刊出版商，且url字段包含该出版商的域名 ...
... {key}由JSON对象中的对应字段内容填入，并逐字检查避免填错，尤其是{url} ...
```

> [!warning] 这些 JSON 对象是**高度简化**的搜索结果。`snippet` 字段是网页摘要，不见得是文章摘要。如果检索要求超出 JSON 对象的内容记载范畴（如具体公式推导），LLM 就有**很高概率靠编来满足需求**。

## 浏览网页功能

*Gemini 3* 支持**浏览网页**（browse），可以点进 URL 链接查看网页具体内容（获取 .html 文件）。

可以让 LLM 对搜索结果做更全面的可靠性检验：

```prompt
对于搜索结果的JSON对象，请务必进入url浏览原始页面 ...
```

> [!note] 原生 *DeepSeek* 不支持浏览网页功能。

对于不支持浏览网页的 LLM，或仅需快速检索的任务，用基本模板提示词即可。
